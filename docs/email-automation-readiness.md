### 2. Make eligibility fail closed, including error paths

Observed risks: the worker treats a missing price-email preference as enabled (`!== false`); the alert claim SQL defaults missing email preferences to true. Several suppression queries ignore database errors and treat absent returned data as no suppression.

Require an explicit true email flag, a confirmed usable email address, no applicable suppression, and successful reads before sending. Database/auth lookup errors must defer or fail the work, never authorize email. Recheck immediately before provider submission and propagate failed writes instead of reporting success.

Preserve current users' saved flags. However, the five existing true price-email flags are not evidence of five explicit opt-ins: the former default was true. Broad price-alert rollout needs a documented legacy-consent policy or renewed user choice; do not silently rewrite users' settings or infer consent from onboarding completion.

### 3. Isolate the pilot before any queue mutation

Both edition/brief enqueuers currently enumerate all opted-in users. The worker applies its internal allowlist **after** claiming rows and cancels non-allowlisted rows. Only News Highlights currently selects the category-specific claim RPC; a Market Brief/category argument otherwise falls through to the global claim.

Add server-controlled pilot recipient scope and an explicit category to both enqueue and claim paths. Unknown categories must be rejected, not interpreted as “all.” A pilot must neither enqueue, claim nor cancel another user's or another category's work. Do not temporarily disable other users' consent to create isolation.

Separate content generation from recipient enqueueing, or provide a real no-write dry-run. **The current worker's `disabled` mode is not a read-only dry-run:** it claims and cancels rows. Do not use it for preflight checks.

### 4. Harden duplicate prevention and recovery

Existing strengths: unique database event keys, atomic `FOR UPDATE SKIP LOCKED` queue claims, three-attempt limit, and Resend idempotency headers.

Remaining risks and required tests:

- Freeze the serialized provider request for a given event key. The current unsubscribe expiry is regenerated on each attempt and Market Brief reads live watchlist values; retry bodies can change under the same key.
- Fence updates to the current claim owner and renew/size leases for actual processing time. A serial batch of 25 × 20-second provider timeouts can exceed the 120-second lease, before database/auth work is counted.
- Treat failed acknowledgement writes as failures to reconcile, not confirmed success. Never blindly resend an ambiguous accepted request.
- Reconcile acceptance before retrying after the provider's 24-hour idempotency retention. Preserve durable event identity beyond that window.
- Recover exhausted processing rows, and prevent a late old worker from overwriting a newer claim or delivery event.
- Allow only one builder to publish a given news edition; current upsert-based builds can race and overwrite ready/failed state.

### 5. Preserve data-quality gates and support advertised alerts

The evening coordinator must generate for the intended Nairobi market date, check `ready`, and enqueue **that returned overview ID**. Do not select an arbitrary previous “latest ready” overview if today's build fails. Set a delivery cutoff so yesterday's retry does not arrive as today's brief. Keep the 90% validated-stock threshold and extreme-move checks; investigate excluded/stale source data rather than lower the threshold to force mail.

News remains stored, quality-checked data only, with three qualifying articles minimum. Keep its existing 06:00 EAT window boundary even if dispatch starts later. A skipped edition is a legitimate no-send outcome. Define whether insufficient articles may be retried after ingestion completes; currently the coordinator exits immediately for `skipped` editions, and its explicit retry flag only retries `failed`.

The UI advertises stocks, FX, commodities and funds plus percentage-change conditions; the deployed evaluator/claim currently implements stocks and above/below thresholds only. Implement and test missing coverage without deleting features. Keep price automation off until coverage matches the UI, or get explicit approval for a clearly labelled limited pilot. Checking every minute cannot produce real-time prices when source ingestion is hourly: describe alerts as firing after the next fresh supported update.

### 6. Complete delivery and preference lifecycle handling

The webhook verifies signatures, but currently persists only delivered/bounced/complained; configured failed/delayed events are ignored, and suppressed events are not subscribed. Store supported delivery failures/delays/suppressions; reject invalid signatures; make duplicate/out-of-order events safe; return retryable errors when persistence fails. Never let an out-of-order delivered event erase a complaint/suppression.

One-click unsubscribe writes a suppression as well as setting the preference false. The current Settings switch only changes the boolean, so switching back on does not lift a prior unsubscribe suppression. Implement a deliberate authenticated re-subscribe flow for the user's own unsubscribe suppression only. Hard-bounce, complaint and admin suppressions must remain protected.

## Monitoring and rollback

For each run record: run/category/date, eligible count, newly queued count, provider accepted/delivered/failed counts, skipped reason, oldest pending age and duplicate/lease anomalies. Keep secret values and recipient addresses out of routine logs. Alert the operator on missing expected runs, prolonged processing, provider failures, webhook errors, unexpected recipient counts and quality-blocked editions.

Prepare a pause switch that stops new enqueue/claim work without deleting or cancelling unrelated rows. On an incident, disable only the newly approved communication jobs through supported cron APIs, stop additional dispatch, and reconcile already-in-flight provider submissions. Disabling cron cannot recall an email already accepted. Do not use the existing mutating `disabled` worker as a queue-preserving rollback.
